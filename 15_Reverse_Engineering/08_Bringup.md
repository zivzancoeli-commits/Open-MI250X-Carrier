# Bring-up

# Purpose

Create a numbered engineering bring-up checklist for an AMD Instinct MI250X OAM carrier-board prototype using only repository-supported evidence. This procedure covers power verification, clock verification, management verification, PCIe enumeration, firmware, ROCm, health checks, validation, debug flow, and error recovery.

This file is a gated procedure template, not an executable lab script. The repository does not currently contain verified rail names, voltages, currents, timing values, PMBus addresses, firmware commands, PCIe lane maps, REFCLK frequency, reset timing, or health-check pass/fail limits. Missing values remain `Unknown` instead of being filled from assumptions.

| 9.3 | Debug in dependency order. | Check power before clocks, clocks before reset, reset before PCIe, PCIe before ROCm, management/telemetry before health, cooling before sustained load. | Stop if an earlier dependency is unverified. | `15_Reverse_Engineering/02_Power_Rails.md`; `15_Reverse_Engineering/03_Clock_Tree.md`; `15_Reverse_Engineering/05_PCIe.md`; `15_Reverse_Engineering/04_Management.md` |
| 9.4 | Compare observed behavior only against sourced expectations. | Use sourced pass/fail limits and requirements for each signal, bus, rail, clock, or software check. | Stop if expected behavior is unknown; create a research item instead of guessing. | `README.md`; `AI_TASKS.md`; `09_AI_Notes/10_Design_Checklist.md` |
| 9.5 | Separate hardware enumeration failures from ROCm/software failures. | If hardware does not enumerate, return to power/clock/reset/PCIe; if hardware enumerates but ROCm fails, collect ROCm/driver/software logs. | Stop if trying ROCm workarounds before electrical enumeration is stable. | `13_Reference_Docs/ROCm/Overview.md`; `15_Reverse_Engineering/05_PCIe.md`; `15_Reverse_Engineering/10_Minimal_Carrier.md` |
| 9.6 | Record root cause or unresolved evidence gap. | Debug log identifies confirmed root cause, unresolved source requirement, or next research document to obtain. | Stop before retrying if root cause is unknown and failure could damage hardware. | `15_Reverse_Engineering/02_Power_Rails.md`; `15_Reverse_Engineering/04_Management.md`; `15_Reverse_Engineering/06_Mechanical.md` |

# Procedure 10: Error Recovery

| Step | Engineering procedure | Required evidence / result | Stop condition | Sources |
|---:|---|---|---|---|
| 10.1 | Recover from power faults by entering a sourced safe-power-down sequence. | Power-down order, enable behavior, discharge/precharge, retry conditions, and fault-latch behavior are sourced. | Stop if shutdown order, fault behavior, or retry criteria are unknown. | `15_Reverse_Engineering/02_Power_Rails.md`; `18_Component_Research/02_Power_Converters.md`; `18_Component_Research/09_Power_Connectors.md` |
